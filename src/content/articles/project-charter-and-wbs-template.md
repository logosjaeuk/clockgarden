## 1. 프로젝트의 80%는 '초기 정의 단계'에서 실패합니다

프로젝트가 중도에 좌초하거나 마감 직전에 일정과 예산이 터지는 원인은 대개 실행력의 문제가 아닙니다. 프로젝트를 시작할 당시 **"이 프로젝트가 왜 필요하고, 정확히 어디까지 만들 것이며, 성공의 기준이 무엇인가"**를 문서로 합의하지 않은 채 주먹구구식으로 출발했기 때문입니다.

글로벌 프로젝트 관리 표준(PMI/PMBOK)에서 가장 첫 번째 산출물로 강조하는 것이 바로 **프로젝트 헌장(Project Charter)**과 **작업 분류 체계(WBS)**입니다.

현업에서 즉시 복사해 사용할 수 있는 실전 프로젝트 기획서 표준 서식과 WBS 계층 설계법을 상세히 정리합니다.

---

## 2. 프로젝트 기획서(Project Charter) 필수 8대 구성 요소

완성도 높은 기획서는 길고 장황한 50페이지짜리 파워포인트가 아닙니다. 이해관계자(의사결정권자, 개발팀, 기획팀, 디자인팀)가 단 2페이지 안에서 모든 핵심을 명확히 이해할 수 있는 표준 서식이어야 합니다.

| 구성 항목 | 핵심 질문 | 기재 예시 |
| :--- | :--- | :--- |
| **1. 배경 및 필요성** | 왜 지금 이 프로젝트를 시작해야 하는가? | 기존 결제 프로세스의 높은 이탈률(42%) 개선 |
| **2. 최종 목표 (Goal)** | 이 프로젝트로 달성할 정량적 결과는 무엇인가? | 간편결제 도입을 통한 결제 완료율 20%p 개선 |
| **3. 범위 (Scope - In/Out)** | 이번 프로젝트에 포함되는 것과 제외되는 것은? | [In] 카카오페이/토스 연동, [Out] 글로벌 해외 결제 |
| **4. 주요 마일스톤** | 언제 어떤 굵직한 중간 산출물이 나오는가? | 1단계: 기획 확정 (11/15), 2단계: 개발 검증 (12/10) |
| **5. 핵심 이해관계자** | 프로젝트 총괄(PM)과 최종 승인자(Sponsor)는? | 스폰서: 사업본부장, PM: 김철수 팀장, 개발 리드: 박영희 |
| **6. 예산 및 리소스** | 투입되는 비용과 인력 규모는? | 총 개발 외주비 3,500만 원, 내부 투입 M/M: 4.5 |
| **7. 식별된 위험 (Risks)** | 실패할 수 있는 주요 리스크와 대응 방안은? | PG사 심사 지연 위험 ➔ 사전 계약 절차 병행 착수 |
| **8. 성공 측정 지표 (KPI)** | 프로젝트 완료 후 3개월 뒤 무엇으로 평가할 것인가? | 런칭 후 30일간 간편결제 거래액 5억 원 달성 |

> [!IMPORTANT]
> 특히 **'프로젝트 범위 제외(Out of Scope)'**를 명시하는 것은 생명과도 같습니다. 기획서에 "이것은 이번 1차 릴리스에서 개발하지 않는다"를 명문화해 두지 않으면, 중간에 임원이나 유관 부서의 추가 요구사항(Scope Creep)이 끊임없이 밀려들어 일정 전체가 파탄 납니다.

## 3. 실무 WBS(Work Breakdown Structure) 계층 구조 설계

프로젝트 기획서가 승인되었다면, 목표를 쪼개어 실제 업무 단위로 분해하는 WBS 작업에 착수합니다. WBS는 통상 3단계 계층으로 분할할 때 관리 효율이 가장 높습니다:

```
[Level 1: 마일스톤 / 대분류 (Phase)]
  └── [Level 2: 작업 패키지 / 중분류 (Work Package)]
        └── [Level 3: 실행 액션 단위 / 소분류 (Task)]
```

| WBS 코드 | 작업명 (Task Name) | 산출물 (Deliverable) | 담당자 | 시작일 | 종료일 | 선행 작업 | 진행 상태 |
| :---: | :--- | :--- | :---: | :---: | :---: | :---: | :---: |
| **1.0** | **기획 및 요구사항 정의** | 최종 기획서 PDF | 김기획 | 11/01 | 11/15 | - | 완료 |
| 1.1 | 고객 여정 및 결제 플로우 분석 | 플로우차트 | 김기획 | 11/01 | 11/05 | - | 완료 |
| 1.2 | UI/UX 와이어프레임 설계 | 피그마 시안 v1.0 | 이디자인 | 11/06 | 11/12 | 1.1 | 진행중 |

## 4. WBS 작성 시 반드시 지켜야 할 '100% 룰'

1. **상위 작업은 하위 작업의 100% 합이어야 합니다:** 하위 작업들을 모두 완수했을 때 상위 마일스톤이 누락 없이 100% 완성되어야 합니다.
2. **동사 중심의 명확한 액션 정의:** `"결제 모듈"`처럼 모호하게 쓰지 말고, `"결제 API 모듈 개발 및 단위 테스트 완료"`처럼 구체적인 완료 상태를 기술하세요.
3. **8-80 시간 원칙:** 최하위 작업(Task)의 소요 시간은 최소 8시간(1일), 최대 80시간(2주)을 넘지 않도록 쪼개야 진척 관리가 가능합니다.

## 5. 결론: 기획서가 단단해야 퇴근이 빨라집니다

잘 작성된 프로젝트 기획서와 WBS는 프로젝트 진행 중 이해관계자 간의 갈등이나 오해가 발생했을 때 가장 강력한 **'단 하나의 진실의 원천(Single Source of Truth)'** 역할을 합니다.

일정 지연과 끝없는 수정 요청에 시달리고 있다면, 다음 프로젝트부터는 반드시 본 템플릿 서식을 프로젝트 착수 킥오프 미팅에서 공식 공유하고 서명을 받은 뒤 진행해 보세요.
